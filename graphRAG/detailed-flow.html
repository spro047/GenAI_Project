Flow 1 — Quick Mode: Text → Knowledge Graph

10 steps

The user pastes text into the left sidebar and clicks "Generate Graph". This triggers a POST /generate request. Everything happens server-side in ~10–20s.

⑥ Graph Construction — Deep Dive

StepWhat happensKey detail
Alias Resolution Pre-built map: {"belly":"Isabel Conklin", "isabel":"Isabel Conklin"} + alias_predicates = {KNOWN_AS, ALSO_KNOWN_AS, ALIAS} If a triple's predicate is an alias predicate, the objects become alias entries. Alias edges themselves are skipped.
Entity Normalization normalize_entity() resolves aliases, merges fragments ("Musk"→"Elon Musk" if seen), strips leading "The " if not formal Two-word+ entities are registered as canonical names for fragment merging.
Type Inference infer_type() checks 10 categories in priority order: STOP_WORDS→PERSON (title words)→AI_MODEL→PRODUCT→ORGANIZATION→LOCATION→EVENT→LEGISLATION→GOVERNMENT→TECHNOLOGY→PERSON (2-3 cap words)→CONCEPT Each category has its own keyword set. Eg org_words = {'university','company','corp','inc','llc','ltd','government','court',...}
Edge Dedup Before adding: check if any existing edge has (source==s_id AND target==o_id) OR (source==o_id AND target==s_id) with same label This prevents A→B and B→A with same relationship from duplicating.

Flow 2 — Ask a Question (Hybrid GraphRAG)

7 steps

The user types a question in the chat panel. The system combines graph structure (who's connected to whom) with semantic vector search (original text paragraphs) to build a super-context for the LLM.

③ Graph Context — How It Works

Global query detection: The function get_graph_context() checks for keywords like "summarize", "overall", "everything", "relationships", "structure". If found AND query is under 15 words → global mode: includes top 15 nodes + top 30 edges. ALSO: if the graph has ≤ 15 nodes, it auto-switches to global mode.
Entity matching: For specific queries, it matches the query text against node labels. Tries exact match first, then partial keyword overlap. For each matched node, collects all edges where node appears as source or target (1-hop neighbors). Returns ENTITIES: + RELATIONSHIPS: sections.

④ Vector Context — How It Works

Chunking strategy

The original text is split by \n\n (paragraphs). If it's one long paragraph (>800 chars), it uses 800-char sliding windows with 600-char overlap. Each chunk gets ID: chunk_{first10alphanumeric}_{index}.

Query with timeout

get_vector_context_with_timeout() wraps the ChromaDB query in a daemon thread with 500ms timeout. If the DB is slow/stuck, the vector context is skipped rather than blocking the response.

Similarity search

ChromaDB collection "knowledge_graph_chunks" with cosine distance. Uses DefaultEmbeddingFunction (SentenceTransformers) locally, ONNXMiniLM_L6_V2 on Vercel. Returns top 3 chunks.

Super-context prompt

The final prompt sent to the LLM contains: GRAPH CONTEXT (facts like "Paul Atreides CHILD_OF Duke Leto") + VECTOR CONTEXT (narrative paragraphs) + CONVERSATION HISTORY (last 5 turns) + RULES (detailed answer, follow-ups mandatory).

Flow 3 — Workspace / Multi-Document Mode

5 steps

Unlike Quick Mode (browser-only localStorage), Workspace Mode persists everything to SQLite. You can create projects, ingest multiple documents, generate a graph per document, and merge them.

④ Merge Logic — Deep Dive

AspectHow it works
Node dedupKeyed by lowercase label. First occurrence wins. If same label has different descriptions, they're concatenated with " | ". Aliases are merged.
Edge dedupKeyed by (source_label, label, target_label) tuple. Old IDs are resolved to labels via id_to_label map within each sub-graph, then mapped to new merged IDs.
Community recalcAfter merge, compute_communities() re-runs DFS connected components on the unified graph.
Note: The merge only unions graphs — it does not run the extraction pipeline again. Each document's graph was generated independently during POST /ingest.

Other API Endpoints

6 more

🖱️ Describe Node POST /describe_node

Sends entity name + context text to LLM. If context is empty or short (<30 chars), queries ChromaDB for richer context as fallback. If nothing available, uses world-knowledge prompting ("Provide a concise 1-2 sentence factual description..."). Returns plain text description.

🔍 Drill Down POST /drill_down

Deep-dive into one entity. Searches context_text for entity-matching paragraphs + ChromaDB for 5 additional chunks. Sends specialized prompt: "Extract niche relationships specifically involving '{entity}'" → parses triples → builds sub-graph. Falls back to fallback_extract(target_entity=entity_name) filtered to only triples involving that entity.

📊 Generate Report POST /generate_report

Computes graph metrics programmatically: top-5 degree centrality, isolated nodes (degree=0), bridge nodes (neighbors >2 but <n/2), relationship type counts. Sends all metrics to LLM with a 7-section report template (Title, Executive Overview, Structural Analysis, Relationship Explanation, Community Insights, Patterns, Recommendations). Returns Markdown report.

📄 Export PDF POST /export_pdf

Receives the Markdown report, strips markdown syntax (**, ###, #, * → -), sanitizes to Latin-1 encoding, renders via fpdf2 with Helvetica font. Returns Knowledge_Graph_Report.pdf as downloadable attachment.

💾 Save / Delete Graph

POST /save_graph: writes current graph JSON to graph_data.json on disk (manual override). POST /delete_graph: reconstructs chunk IDs from the text and calls vdb_collection.delete(ids=...) to clean up ChromaDB.

ℹ️ Model Info GET /model_info

Returns the active model based on the priority chain. Frontend calls this on page load to show the live model status (not cached from previous graphs). JSON: {active_model, huggingface_model, use_local_gguf, use_local_llm}.
